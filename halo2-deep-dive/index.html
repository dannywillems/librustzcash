17 - Halo 2 deep dive

Goal​

Chapter 05 introduced Halo 2 at a black-box level. This chapter goes under the hood: the PLONKish arithmetisation, the polynomial-IOP machinery, the lookup argument, the inner-product argument (IPA) that underlies the polynomial commitment, the Fiat-Shamir transcript, and the specific custom gates used by Orchard.

You do not need to implement Halo 2; the halo2_proofs crate already does. But you must understand it well enough to:

  • Read an Orchard circuit module and pair it with the math.
  • Reason about soundness when reviewing changes.
  • Estimate proof size and verifier cost for new circuit features.

1. The PLONKish circuit model​

A PLONKish circuit is a rectangular table with NNN rows and a small number of columns. Each column has a type:

  • Advice (or witness): values the prover supplies.
  • Fixed: values baked into the circuit (constants, lookup tables, selectors).
  • Instance: values that are part of the public input.

The verifier's view of the prover's commitment is one polynomial per column, interpolated over a multiplicative subgroup H⊆F∗H \subseteq \mathbb{F}^*H⊆F∗ of size NNN. Let ω\omegaω be a primitive NNN-th root of unity generating HHH.

For column WWW, define w(X)∈F[X]w(X) \in \mathbb{F}[X]w(X)∈F[X] to be the unique polynomial of degree <N< N<N with w(ωi)=Wiw(\omega^i) = W_iw(ωi)=Wi​ for i=0,…,N−1i = 0, \ldots, N-1i=0,…,N−1.

2. Custom gates​

A custom gate is a polynomial equation that must hold at every row, possibly involving cells in nearby rows (via shifting by ωj\omega^jωj):

G(w1(X),w2(X),…,w1(ωX),w2(ωX),…,q(X))  =  0for all X∈H.G(w_1(X), w_2(X), \ldots, w_1(\omega X), w_2(\omega X), \ldots, q(X)) \;=\; 0 \quad \text{for all } X \in H.G(w1​(X),w2​(X),…,w1​(ωX),w2​(ωX),…,q(X))=0for all X∈H.

Here q(X)q(X)q(X) is a selector, a fixed polynomial that is 111 on rows where the gate is "on" and 000 elsewhere; multiplying the gate by q(X)q(X)q(X) disables it on irrelevant rows.

Custom gates are how Halo 2 supports operations natively. Orchard uses custom gates for:

  • Pallas point addition (ec_add).
  • Pallas point doubling (ec_double).
  • Scalar multiplication ("scalar_mul" group of gates).
  • Sinsemilla hash chains.
  • ECDH and Poseidon.
  • Field arithmetic and bit decomposition.

Each gate is a (usually low-degree) polynomial identity. Halo 2 combines them all into one identity by random linear combination at proving time.

3. The vanishing argument​

To enforce G(…)=0G(\ldots) = 0G(…)=0 on HHH, the prover commits to a quotient polynomial t(X)t(X)t(X) such that

G(…)  =  t(X)⋅ZH(X),ZH(X)  =  ∏ωi∈H(X−ωi)  =  XN−1.G(\ldots) \;=\; t(X) \cdot Z_H(X), \qquad Z_H(X) \;=\; \prod_{\omega^i \in H} (X - \omega^i) \;=\; X^N - 1.G(…)=t(X)⋅ZH​(X),ZH​(X)=ωi∈H∏​(X−ωi)=XN−1.

This is the vanishing polynomial argument. If the identity holds on HHH, GGG is divisible by ZHZ_HZH​; if not, no t(X)t(X)t(X) of bounded degree exists. The verifier challenges with a random ζ\zetaζ and checks

G(evaluations at ζ)=?t(ζ)⋅ZH(ζ).G(\text{evaluations at } \zeta) \stackrel{?}{=} t(\zeta) \cdot Z_H(\zeta).G(evaluations at ζ)=?t(ζ)⋅ZH​(ζ).

By Schwartz-Zippel, the probability of a malicious prover passing this check with an incorrect identity is at most deg⁡(G)/∣F∣\deg(G) / |\mathbb{F}|deg(G)/∣F∣ which is negligible.

4. The permutation argument (copy constraints)​

A Halo 2 circuit needs to enforce equalities between cells in different rows (e.g. "the output of row 5 is the input of row 7"). This is the copy constraint problem.

The PLONK permutation argument represents the constraint as a permutation σ\sigmaσ on cell positions. Define a "grand product" polynomial z(X)z(X)z(X) satisfying:

z(ωX)z(X)  =  ∏j(wj(X)+β⋅σj(X)+γ)∏j(wj(X)+β⋅jid(X)+γ),\frac{z(\omega X)}{z(X)} \;=\; \frac{\prod_{j} (w_j(X) + \beta \cdot \sigma_j(X) + \gamma)}{\prod_{j} (w_j(X) + \beta \cdot j_{\text{id}}(X) + \gamma)},z(X)z(ωX)​=∏j​(wj​(X)+β⋅jid​(X)+γ)∏j​(wj​(X)+β⋅σj​(X)+γ)​,

for random verifier challenges β,γ\beta, \gammaβ,γ. The prover commits to z(X)z(X)z(X) and proves it has the right shape; the verifier checks multiplicatively that zzz ends where it started (so the permutation is closed) and that the boundary condition holds.

This is a O(Nlog⁡N)O(N \log N)O(NlogN) FFT-time argument that costs the verifier O(1)O(1)O(1) extra evaluations.

5. The lookup argument​

Halo 2 includes a lookup table mechanism: rows of a designated "lookup" table set TTT are precomputed, and the protocol enforces that for each row iii, the tuple of values in specific columns (wj1(ωi),wj2(ωi),…)(w_{j_1}(\omega^i), w_{j_2}(\omega^i), \ldots)(wj1​​(ωi),wj2​​(ωi),…) is some row of TTT.

The argument is a variant of plookup: define

ϕ(X)=∑iai⋅Xi,ψ(X)=∑ibi⋅Xi,\phi(X) = \sum_{i} a_i \cdot X^i, \quad \psi(X) = \sum_{i} b_i \cdot X^i,ϕ(X)=i∑​ai​⋅Xi,ψ(X)=i∑​bi​⋅Xi,

with aia_iai​ the multiplicity of the iii-th lookup input and bib_ibi​ the table-row counter; the prover proves ϕ\phiϕ and ψ\psiψ are related by an inner-product-style identity. The cost is O(N+∣T∣)O(N + |T|)O(N+∣T∣).

Orchard uses lookups heavily:

  • Sinsemilla's chunk lookup: 10-bit chunk →\to→ point in a precomputed table S(m)S(m)S(m).
  • Range checks: nnn-bit range check is just a lookup against the table of {0,1,…,2n−1}\{0, 1, \ldots, 2^n - 1\}{0,1,…,2n−1}.
  • Decomposition lookups: assertion that a field element decomposes into specific-size limbs.

6. The transcript​

Halo 2 is non-interactive via Fiat-Shamir. The verifier's challenges β,γ,ζ,…\beta, \gamma, \zeta, \ldotsβ,γ,ζ,… are derived from hashes of the prover's commitments and the public input.

The transcript is implemented by halo2_proofs::transcript::Transcript:

  • write_point(P): hash the encoding of PPP into the state.
  • write_scalar(s): hash sss into the state.
  • squeeze_challenge() -> Scalar: derive a challenge from the current state.

The hash function used is Poseidon over the Pallas base field for in-circuit transcripts (when verifier-of-verifier composition is needed) and BLAKE2b for the on-disk transcript.

Domain separation:

  • Each transcript has a personalisation byte string identifying the circuit and version.
  • Public inputs are absorbed before any commitment so that the proof is bound to the specific public input.

7. The Inner Product Argument (IPA)​

This is the polynomial commitment scheme in Halo 2. A polynomial p(X)=∑aiXip(X) = \sum a_i X^ip(X)=∑ai​Xi of degree <n< n<n is committed to as

Comm(p)  =  ∑i=0n−1[ai]Gi  ∈  EPallas,\mathsf{Comm}(p) \;=\; \sum_{i=0}^{n-1} [a_i] G_i \;\in\; E_{\text{Pallas}},Comm(p)=i=0∑n−1​[ai​]Gi​∈EPallas​,

with fixed deterministic bases {Gi}i=0n−1\{G_i\}_{i=0}^{n-1}{Gi​}i=0n−1​. To prove an opening p(z)=vp(z) = vp(z)=v, the protocol:

  1. Sample challenge xxx via Fiat-Shamir.

  2. Bisect the coefficient vector a⃗=(a⃗L,a⃗R)\vec{a} = (\vec{a}_L, \vec{a}_R)a=(aL​,aR​) and similarly G⃗=(G⃗L,G⃗R)\vec{G} = (\vec{G}_L, \vec{G}_R)G=(GL​,GR​).

  3. Compute "cross-terms":

    Lk=∑[aL,i]GR,i+[uk]H,Rk=∑[aR,i]GL,i+[uk−1]H,L_k = \sum [a_{L,i}] G_{R,i} + [u_k] H, \qquad R_k = \sum [a_{R,i}] G_{L,i} + [u_k^{-1}] H,Lk​=∑[aL,i​]GR,i​+[uk​]H,Rk​=∑[aR,i​]GL,i​+[uk−1​]H,

    where HHH is a fixed auxiliary generator and uku_kuk​ is a per-round random.

  4. Fold: a⃗′=a⃗L+uka⃗R\vec{a}' = \vec{a}_L + u_k \vec{a}_Ra′=aL​+uk​aR​, G⃗′=G⃗L+uk−1G⃗R\vec{G}' = \vec{G}_L + u_k^{-1} \vec{G}_RG′=GL​+uk−1​GR​.

  5. Recurse on (a⃗′,G⃗′)(\vec{a}', \vec{G}')(a′,G′).

After log⁡2n\log_2 nlog2​n rounds, the final a⃗\vec{a}a is a single scalar; the prover sends it and the verifier checks a final equation.

Proof size and verifier cost​

  • Proof size: O(log⁡n)O(\log n)O(logn) group elements (the Lk,RkL_k, R_kLk​,Rk​ pairs) plus one scalar.
  • Verifier cost: O(n)O(n)O(n) scalar mults to recompute G⃗′\vec{G}'G′ at the end. Halo 2 amortises this across multiple proofs ("accumulation").

Compared to KZG (used by other PLONK variants): KZG verification is O(1)O(1)O(1) pairings, but needs a trusted setup. IPA verification is O(n)O(n)O(n) MSM, no trusted setup. The Halo 2 design trades verifier cost for setup transparency.

Accumulation / Halo​

The original Halo paper observed that the IPA verifier's O(n)O(n)O(n) MSM can be deferred: instead of evaluating, commit to a deferred verification statement and pass it forward. Across kkk proofs, a single accumulated MSM checks all of them at the end. This is recursion.

Orchard does not currently use this in production (each Orchard bundle is verified directly), but Halo 2 was chosen for the option to enable it in future (chain-history accumulators, recursive proof verification in-block).

8. The Pallas/Vesta cycle and recursion​

To verify a Halo 2-over-Pallas proof inside another Halo 2 proof, the inner verifier circuit would have to perform arithmetic over the base field of Pallas. That base field is the scalar field of Vesta. Building the verifier as a Halo 2-over-Vesta circuit makes it efficient (the verifier's native operations are scalar ops in Fp\mathbb{F}_pFp​, which are Vesta's scalar field).

Symmetrically, a Vesta proof can be verified inside a Pallas circuit. This bidirectional capability is what makes the cycle useful.

Orchard does not exploit this yet. Future work (chapter 21) does.

9. Custom gates used by Orchard - sample​

Reading the orchard::circuit module, you will find groups of custom gates implementing each cryptographic primitive.

Example (paraphrased): the "incomplete addition" custom gate for Sinsemilla. Given P1=(x1,y1)P_1 = (x_1, y_1)P1​=(x1​,y1​) and P2=(x2,y2)P_2 = (x_2, y_2)P2​=(x2​,y2​) with P1≠±P2P_1 \neq \pm P_2P1​=±P2​, the sum P3=(x3,y3)P_3 = (x_3, y_3)P3​=(x3​,y3​) satisfies:

λ=y2−y1x2−x1,x3=λ2−x1−x2,y3=λ(x1−x3)−y1.\lambda = \frac{y_2 - y_1}{x_2 - x_1}, \qquad x_3 = \lambda^2 - x_1 - x_2, \qquad y_3 = \lambda(x_1 - x_3) - y_1.λ=x2​−x1​y2​−y1​​,x3​=λ2−x1​−x2​,y3​=λ(x1​−x3​)−y1​.

As polynomial identities:

λ⋅(x2−x1)  −  (y2−y1)  =  0,\lambda \cdot (x_2 - x_1) \;-\; (y_2 - y_1) \;=\; 0,λ⋅(x2​−x1​)−(y2​−y1​)=0, x3  +  x1  +  x2  −  λ2  =  0,x_3 \;+\; x_1 \;+\; x_2 \;-\; \lambda^2 \;=\; 0,x3​+x1​+x2​−λ2=0, y3  −  λ(x1−x3)  +  y1  =  0.y_3 \;-\; \lambda (x_1 - x_3) \;+\; y_1 \;=\; 0.y3​−λ(x1​−x3​)+y1​=0.

These three identities are enforced by three custom-gate rows when the appropriate selector is on. The "λ\lambdaλ" is an extra advice column.

The completeness assumption (P1≠P2P_1 \neq P_2P1​=P2​) is enforced by an explicit "must be distinct" assertion implemented as another gate. If a malicious prover supplies P1=P2P_1 = P_2P1​=P2​, the λ\lambdaλ-row identity above becomes 0/00/00/0 - meaningless - and the additional distinctness assertion fails.

10. Range checks​

Halo 2 implements nnn-bit range check via a lookup against a precomputed table {0,1,…,2n−1}\{0, 1, \ldots, 2^n - 1\}{0,1,…,2n−1}. For larger bit ranges, decompose into smaller chunks (typically 10-bit) and lookup each.

For example, a 64-bit value vvv is decomposed as v=c0+210c1+220c2+…+260c6v = c_0 + 2^{10} c_1 + 2^{20} c_2 + \ldots + 2^{60} c_6v=c0​+210c1​+220c2​+…+260c6​ with each cic_ici​ in a 10-bit lookup table. This is much cheaper than enforcing 64 boolean constraints.

11. Sinsemilla in-circuit​

Sinsemilla maps 10-bit chunks of the input to Pallas points via a precomputed table SSS. Inside the circuit:

  • The chunk m(i)m^{(i)}m(i) is bit-decomposed and range-checked via lookup.
  • The point S(m(i))S(m^{(i)})S(m(i)) is looked up via the lookup argument against a precomputed table of (chunk,S(chunk))(\text{chunk}, S(\text{chunk}))(chunk,S(chunk)) pairs.
  • The running accumulator AiA_iAi​ is incomplete-added with S(m(i))S(m^{(i)})S(m(i)) using the incomplete-addition gate.
  • After nnn chunks, the result is returned.

The lookup tables for SSS are part of the constraint system fixed columns, baked into the verifying key.

12. The verifier in code​

halo2_proofs::plonk::verify_proof is the entry. It:

  1. Re-derives the structured reference string (the generator vectors).
  2. Initialises the transcript with the public input.
  3. Absorbs the prover's commitments to advice columns.
  4. Squeezes Fiat-Shamir challenges.
  5. Absorbs more commitments and evaluations.
  6. Verifies the polynomial identities at the challenge point.
  7. Verifies the IPA opening proofs.

For Orchard's verifier, orchard::circuit::Circuit::verify_proof wraps this.

13. Proof size, in numbers​

For an Orchard bundle of nnn Actions (over Pallas at k=11k = 11k=11, so N=211N = 2^{11}N=211 rows):

  • Advice columns: ∼6\sim 6∼6.
  • Custom gate selectors: ∼50\sim 50∼50.
  • IPA proof size: ∼32⋅log⁡2N≈350\sim 32 \cdot \log_2 N \approx 350∼32⋅log2​N≈350 B per polynomial, with ∼6\sim 6∼6 polynomials →∼2\to \sim 2→∼2 kB.
  • Plus commitments and final scalars: ∼1.5\sim 1.5∼1.5 kB.
  • Plus permutation and lookup arguments: another ∼1\sim 1∼1 kB.

Total: ~5 kB per bundle, independent of nnn (the circuit is instantiated with nnn Actions in the same single proof).

14. Soundness and security parameters​

Halo 2's soundness:

  • Schwartz-Zippel error: deg⁡/∣Fp∣\deg / |\mathbb{F}_p|deg/∣Fp​∣, with degrees ∼N≈211\sim N \approx 2^{11}∼N≈211 and ∣Fp∣≈2254|\mathbb{F}_p| \approx 2^{254}∣Fp​∣≈2254. Negligible.
  • IPA soundness: reduces to discrete log on Pallas.
  • Fiat-Shamir soundness: random oracle model, with BLAKE2b/Poseidon as the heuristic instantiation.

Concrete security: 128 bits, assuming Pallas DLP is hard. The 256-bit curves are chosen for this.

16. Common pitfalls for new Halo 2 circuit authors​

  • Off-by-one on selectors: a selector that turns on a gate at row iii also turns it on at row iii of an unused region; ensure selectors are zero where you expect them to be.
  • Underconstrained advice cells: the prover can supply any value for an advice cell unless a gate forces it. Forgetting a constraint creates a soundness hole.
  • Incomplete-addition edge cases: the input points must be proved distinct; do not rely on the formula's behaviour at P1=P2P_1 = P_2P1​=P2​.
  • Lookup table collisions: if two different input chunks map to the same lookup-table row, the protocol does not distinguish them. Tables must be injective on the relevant projection.
  • Transcript replay: failure to absorb a commitment or a public input into the transcript before squeezing a challenge breaks Fiat-Shamir.
