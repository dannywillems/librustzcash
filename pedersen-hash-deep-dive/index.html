16 - Pedersen hash deep dive

Goal​

In chapter 04 we sketched the Sapling Pedersen hash. This chapter fills in the full construction: the windowed encoding, the generator derivation, the constraint count, and the security arguments. Pedersen hash is the single most-evaluated cryptographic operation in Sapling (every note commitment, every Merkle-tree hash, every value commitment) so its details deserve attention.

1. The setting​

We work in the prime-order subgroup EJubjub∘E^{\circ}_{\text{Jubjub}}EJubjub∘​ of order ℓJ≈2252\ell_{\text{J}} \approx 2^{252}ℓJ​≈2252. A Pedersen hash takes a bit string m∈{0,1}km \in \{0,1\}^km∈{0,1}k and a domain-separation tag DDD and outputs a curve point. We write Gj(D)G_j^{(D)}Gj(D)​ for the jjj-th generator associated with domain DDD.

2. The windowed encoding​

Group mmm into 3-bit chunks c0,c1,c2,…c_0, c_1, c_2, \ldotsc0​,c1​,c2​,… Each chunk c=(b0,b1,b2)∈{0,1}3c = (b_0, b_1, b_2) \in \{0, 1\}^3c=(b0​,b1​,b2​)∈{0,1}3 is mapped to a signed integer

enc3(c)  =  (1+b0+2b1)(1−2b2)  ∈  {−4,−3,−2,−1,1,2,3,4}.\text{enc}_3(c) \;=\; (1 + b_0 + 2 b_1)(1 - 2 b_2) \;\in\; \{-4, -3, -2, -1, 1, 2, 3, 4\}.enc3​(c)=(1+b0​+2b1​)(1−2b2​)∈{−4,−3,−2,−1,1,2,3,4}.

That is:

(0,0,0)(0, 0, 0)(0,0,0)111
(1,0,0)(1, 0, 0)(1,0,0)222

This is the booth-encoded representation of a 3-bit window with a sign bit. The advantage: in-circuit, doubling the partial sum costs the same as adding it, so the encoding minimises the number of base doublings needed.

3. Segments​

Combine 63 consecutive chunks into one segment. A segment encodes 3×63=1893 \times 63 = 1893×63=189 bits of input. Within a segment of chunks c0,…,c62c_0, \ldots, c_{62}c0​,…,c62​, define the segment-scalar

⟨ ⁣⟨c0,…,c62⟩ ⁣⟩  =  ∑i=062enc3(ci)⋅24i.\langle\!\langle c_0, \ldots, c_{62} \rangle\!\rangle \;=\; \sum_{i=0}^{62} \text{enc}_3(c_i) \cdot 2^{4i}.⟨⟨c0​,…,c62​⟩⟩=i=0∑62​enc3​(ci​)⋅24i.

The factor 24i2^{4i}24i (not 23i2^{3i}23i) is chosen because each window contributes a value in {−4,…,4}\{-4, \ldots, 4\}{−4,…,4}, which needs four bits to encode unambiguously. The spacing 24i2^{4i}24i keeps the segment scalars uniquely decodable.

A segment scalar lies in approximately

(∑i=062−4⋅24i,  ∑i=0624⋅24i)  ≈  (−415⋅2252,  415⋅2252).\Bigl(\sum_{i=0}^{62} -4 \cdot 2^{4i}, \; \sum_{i=0}^{62} 4 \cdot 2^{4i}\Bigr) \;\approx\; \Bigl(-\tfrac{4}{15} \cdot 2^{252}, \; \tfrac{4}{15} \cdot 2^{252}\Bigr).(i=0∑62​−4⋅24i,i=0∑62​4⋅24i)≈(−154​⋅2252,154​⋅2252).

This is comfortably less than ℓJ\ell_{\text{J}}ℓJ​ so the scalar-mul [⟨ ⁣⟨…⟩ ⁣⟩]Gj[\langle\!\langle \ldots \rangle\!\rangle] G_j[⟨⟨…⟩⟩]Gj​ is meaningful and collision-resistant.

4. Generators per segment​

Each segment jjj has its own generator Gj(D)G_j^{(D)}Gj(D)​ derived deterministically from DDD and jjj:

Gj(D)  =  HashToCurveJubjub ⁣(D ∥ jLE).G_j^{(D)} \;=\; \mathsf{HashToCurve}_{\text{Jubjub}}\!\bigl(D \,\|\, j_{\text{LE}}\bigr).Gj(D)​=HashToCurveJubjub​(D∥jLE​).

The actual hash_to_curve used is a try-and-increment construction:

  1. Compute h=BLAKE2s-256("Zcash_PH" ∥ D ∥ jLE ∥ counter)h = \mathsf{BLAKE2s\text{-}256}(\text{"Zcash\_PH"} \,\|\, D \,\|\, j_{\text{LE}} \,\|\, \text{counter})h=BLAKE2s-256("Zcash_PH"∥D∥jLE​∥counter).
  2. Interpret hhh as a candidate vvv-coordinate. Recover uuu from the curve equation; if no valid uuu exists, increment the counter and retry.
  3. Multiply by the cofactor hJ=8h_{\text{J}} = 8hJ​=8 to land in the prime-order subgroup.

This is deterministic (no randomness) so any party can recompute the same generator set; it is also uniform in EJubjub∘E^{\circ}_{\text{Jubjub}}EJubjub∘​ modulo a negligible bias.

Crucially: the discrete log of any Gj(D)G_j^{(D)}Gj(D)​ relative to any other is unknown (and computing it requires solving DLP on Jubjub). Pedersen-hash collision resistance reduces to DLP.

5. The hash value​

Let S(m)S(m)S(m) be the number of segments after padding mmm to a multiple of 189 bits. Define

PHD(m)  =  ∑j=0S(m)−1[ ⟨ ⁣⟨cj,0,…,cj,62⟩ ⁣⟩ ]Gj(D)  ∈  EJubjub∘.\mathsf{PH}_D(m) \;=\; \sum_{j=0}^{S(m)-1} [\,\langle\!\langle c_{j,0}, \ldots, c_{j, 62} \rangle\!\rangle\,] G_j^{(D)} \;\in\; E^{\circ}_{\text{Jubjub}}.PHD​(m)=j=0∑S(m)−1​[⟨⟨cj,0​,…,cj,62​⟩⟩]Gj(D)​∈EJubjub∘​.

The "DDD" tag is used to select different generator sets per domain. The domains in Sapling include:

  • "Zcash_PH" with sub-tags for "NoteCommitment", "MerkleTree", "PRF_nf", etc.
  • Specific personalisations are defined in section 5.4.1.7 of the protocol spec.

6. Collision resistance​

Claim: finding m1≠m2m_1 \neq m_2m1​=m2​ with PHD(m1)=PHD(m2)\mathsf{PH}_D(m_1) = \mathsf{PH}_D(m_2)PHD​(m1​)=PHD​(m2​) is at least as hard as solving DLP on Jubjub.

Proof sketch: A collision yields ∑j[sj]Gj=∑j[sj′]Gj\sum_j [s_j] G_j = \sum_j [s'_j] G_j∑j​[sj​]Gj​=∑j​[sj′​]Gj​ for distinct windowed encodings {sj},{sj′}\{s_j\}, \{s'_j\}{sj​},{sj′​}. Setting Δj=sj−sj′\Delta_j = s_j - s'_jΔj​=sj​−sj′​, we get ∑[Δj]Gj=O\sum [\Delta_j] G_j = \mathcal{O}∑[Δj​]Gj​=O, which expresses a non-trivial linear relation among the GjG_jGj​'s. If the GjG_jGj​'s are chosen so that they have pairwise unknown discrete logs, finding such a relation contradicts DLP.

The actual proof goes through Pedersen's original argument; the windowed encoding does not weaken it because the encoding is injective on its codomain (different chunks produce different signed ints).

7. In-circuit constraint count​

Inside the Sapling Spend/Output Groth16 circuit, computing a Pedersen hash of kkk bits costs approximately

constraints  ≈  k3⋅(constraints per window).\text{constraints} \;\approx\; \tfrac{k}{3} \cdot (\text{constraints per window}).constraints≈3k​⋅(constraints per window).

In sapling-crypto::circuit::pedersen_hash, the actual breakdown (R1CS constraints, per window):

  • 1 constraint to range-check the boolean bits.
  • 2-3 constraints to compute the signed-window scalar from the bits.
  • 5-7 constraints to perform conditional point addition with the per-segment generator (using twisted-Edwards strongly-unified formulas).

Net: ∼6\sim 6∼6 constraints per bit. For the Sapling note commitment (input ≈8+88+256+256=608\approx 8 + 88 + 256 + 256 = 608≈8+88+256+256=608 bits before randomness), that is ∼3600\sim 3600∼3600 constraints. The Merkle tree hash (input ≈512\approx 512≈512 bits) is ∼3000\sim 3000∼3000 constraints, times tree depth 32≈100,00032 \approx 100{,}00032≈100,000 constraints.

This dominates the Spend circuit's constraint budget (~100,000 of ~150,000 total constraints). Optimising Pedersen-hash circuits has been a frequent area of contribution.

8. The "ρ\rhoρ mixing" Pedersen hash​

For the Sapling nullifier, ρ\rhoρ is derived from the commitment and the position via a modified Pedersen-hash called MixingPedersenHash\mathsf{MixingPedersenHash}MixingPedersenHash:

ρ  =  MixingPedersenHash(cm,pos)  =  cm  +  [pos]Gρ,\rho \;=\; \mathsf{MixingPedersenHash}(\mathsf{cm}, \mathsf{pos}) \;=\; \mathsf{cm} \;+\; [\mathsf{pos}] G_{\rho},ρ=MixingPedersenHash(cm,pos)=cm+[pos]Gρ​,

where GρG_{\rho}Gρ​ is a fixed generator. Note: cm\mathsf{cm}cm is itself a Pedersen-hash output (a point), and we add (not concatenate) the position contribution. This keeps ρ\rhoρ a single Jubjub point without re-hashing.

The position is bounded by the tree size (2322^{32}232 leaves), so [pos]Gρ[\mathsf{pos}] G_{\rho}[pos]Gρ​ is a scalar-mul of a small integer; in- circuit this is much cheaper than another full Pedersen hash.

9. NoteCommitment full formula​

Putting it together, the Sapling note commitment is

NoteCommit(rcm,v,gd,pkd)=PHDnc ⁣( vLE,64 ∥ u(gd)LE,255 ∥ u(pkd)LE,255 )  +  [rcm]Rnc,\mathsf{NoteCommit}(\mathsf{rcm}, v, g_d, \mathsf{pk}_d) = \mathsf{PH}_{D_{\text{nc}}}\!\bigl(\, v_{\text{LE},64} \,\|\, u(g_d)_{\text{LE},255} \,\|\, u(\mathsf{pk}_d)_{\text{LE},255} \,\bigr) \;+\; [\mathsf{rcm}] R_{\text{nc}},NoteCommit(rcm,v,gd​,pkd​)=PHDnc​​(vLE,64​∥u(gd​)LE,255​∥u(pkd​)LE,255​)+[rcm]Rnc​,

with RncR_{\text{nc}}Rnc​ a fixed Jubjub generator and u(⋅)u(\cdot)u(⋅) extracting the uuu-coordinate as a 255-bit little-endian string. Inputs total 64+255+255=57464 + 255 + 255 = 57464+255+255=574 bits.

Why use uuu-coordinates instead of full point encodings? Because the uuu-coordinate uniquely identifies a Jubjub point up to sign, and the negation of a valid Sapling diversifier is also a valid encoding. The sign disambiguation does not affect commitment security (we only need the point modulo sign to be unique).

10. MerkleHash full formula​

Layer-aware:

MerkleHashℓ(x,y)=ExtractJubjub ⁣(PHDMH ⁣( ℓLE,6 ∥ xLE,255 ∥ yLE,255 )),\mathsf{MerkleHash}_\ell(x, y) = \mathsf{ExtractJubjub}\!\Bigl( \mathsf{PH}_{D_{\text{MH}}}\!\bigl(\, \ell_{\text{LE},6} \,\|\, x_{\text{LE},255} \,\|\, y_{\text{LE},255} \,\bigr) \Bigr),MerkleHashℓ​(x,y)=ExtractJubjub(PHDMH​​(ℓLE,6​∥xLE,255​∥yLE,255​)),

with ℓ\ellℓ the 6-bit layer index, x,yx, yx,y the 255-bit children. The result is the uuu-coordinate of the Pedersen hash output, as a Fr\mathbb{F}_rFr​ element.

The inclusion of ℓ\ellℓ prevents an attacker who sees MerkleHashℓ(a,b)\mathsf{MerkleHash}_\ell(a, b)MerkleHashℓ​(a,b) from claiming it is also MerkleHashℓ′(a,b)\mathsf{MerkleHash}_{\ell'}(a, b)MerkleHashℓ′​(a,b) at a different layer; the generators differ per layer.

11. Constant-time considerations​

Pedersen-hash evaluation outside the circuit (in the wallet's trial-decryption pipeline, for instance) takes secret input (rcm\mathsf{rcm}rcm, vvv). The implementation must be constant-time.

sapling-crypto::pedersen_hash::pedersen_hash uses constant-time scalar mul via the jubjub crate. The bit-decomposition and chunking work on byte-aligned data; the looping is over public-size inputs.

The Merkle-tree hash inside scanning is not secret-dependent beyond the position of the wallet's note, which the wallet already knows; no constant-time concern.

13. The "personal_crh" exit​

sapling-crypto::pedersen_hash::pedersen_hash returns a jubjub::SubgroupPoint. Callers that need a scalar (e.g. the Merkle hash) extract the uuu-coordinate via to_affine().get_u().

The conversion from Fr\mathbb{F}_rFr​ (the Jubjub base field, equal to the BLS12-381 scalar field) to a Fr\mathbb{F}_rFr​ scalar is direct.

14. Pitfalls​

  • Window bit ordering: a 3-bit window is (b0,b1,b2)(b_0, b_1, b_2)(b0​,b1​,b2​) in little-endian; the enc_3 formula assumes this order. Reversing endianness silently produces wrong hashes.
  • Personalisation tags: every distinct use of Pedersen hash has its own personalisation. Adding a new use and reusing an existing tag is a vulnerability.
  • Generator construction: the hash_to_curve for generators uses BLAKE2s with a specific personalisation. Implementing it with BLAKE2b is wrong; that bug would only manifest by producing different generators than the spec mandates.
  • Layer index width: 6 bits is enough for depth-32 trees but not deeper. If a future protocol uses depth-64 trees, the encoding needs revision.

15. Where this lives in the workspace​

  • sapling-crypto::pedersen_hash::pedersen_hash: the outside-circuit function used by the wallet.
  • sapling-crypto::circuit::pedersen_hash::pedersen_hash: the Bellman-gadget version used inside the Spend/Output circuit.
  • sapling-crypto::constants: the precomputed generator sets per domain.
  • sapling-crypto::primitives::NoteCommitment: the high-level note commitment using Pedersen hash + commitment randomness.
  • sapling-crypto::primitives::MerkleHash: the Merkle-tree hash.

If you want to truly understand Sapling, read these files alongside the protocol spec section 5.4.1.7-8 and verify each formula in this chapter against the code.
